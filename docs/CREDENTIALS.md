> ⚠ **Security warning:** these are sample passwords for the development and demonstration environment. **All of them must be changed before a real deployment.**

### Permissions by user type

**Administrator** — signs in to the administration area:

- View system-wide usage statistics (UC-23)
- Manage default categories: add, edit, deactivate (UC-20)
- Manage users: disable, re-enable, send a password reset link (UC-22)
- Manage system-wide announcements and saving-tip templates (UC-21)
- Adjust business thresholds in `system_settings`

**Student** — signs in to the student portal:

- Record, edit and (soft) delete daily income/expense transactions (UC-07, UC-10)
- Create and manage personal categories (UC-06)
- Set budget limits by category (UC-13)
- View reports, charts and the dashboard (UC-12, UC-15)
- Receive budget alerts, saving tips and monthly insights (UC-14, UC-17, UC-18)
- Import past spending data from a CSV file (UC-11)
- Configure recurring transactions (UC-09)

## How passwords are stored

Passwords are hashed with **bcrypt at cost 10** before they are written to the `users.password_hash` column. The database **never stores a password in plain text** (BR-01).

The corresponding hash values:

| Password | Hash value |
|---|---|
| `Admin@123` | `$2y$10$GRALQlXS7PZicW3k0sEo6uhaRsGS4WeZ1nMfD46o262Z27B0ZqYNa` |
| `Student@123` | `$2y$10$B3/WANQCknajrDNeJMa9g.coT.Cap1t6q0GKmo6k6q1m5KgfW9QJ6` |

> **Technical note:** the hash values above carry the `$2y$` prefix. If the application uses Spring Security's `BCryptPasswordEncoder`, its `matches()` method accepts both the `$2a$` and `$2y$` prefixes, so sign-in works normally. If integration runs into trouble, a new hash can be generated with the project's own `BCryptPasswordEncoder` and updated in `db/05_seed.sql`.

Verify a hash value from the command line:

```bash
htpasswd -bnBC 10 "" 'Admin@123'
```

## Changing the sample passwords

### Option 1 — Use the password reset feature

This is the system's real flow (UC-03). The administrator sends a reset link to the student (UC-22 B4), and the student sets a new password themselves.

### Option 2 — Generate a new hash and update it directly

```bash
htpasswd -bnBC 10 "" 'MatKhauMoi@2026' | tr -d ':\n'
```

Copy the value you get back (dropping the leading `admin:` part) and update:

```sql
UPDATE users SET password_hash = '<new hash value>'
 WHERE email = 'admin@campuscoin.edu';
```

> Because the password is hashed, this `UPDATE` statement cannot be run against a database in read-only mode. In a real environment, change it through the application's own feature so that direct write privileges never have to be granted.

Besides the application accounts above, the MySQL database also has its own connection accounts:

| Purpose | Account | Password | Notes |
|---|---|---|---|
| Application connection | `campuscoin_app` | the `MYSQL_PASSWORD` value in `.env` | Has privileges on the `campuscoin` database only |

| Viewing data through Adminer | `campuscoin_app` | the `MYSQL_PASSWORD` value in `.env` | Sign in at http://localhost:8080 |

Passwords are not written in this document. Copy `.env.example` to `.env` and fill in the values; `.env` is already ignored by `.gitignore`.

## Application secrets

The backend also needs two secrets of its own. Neither is a database account, and neither is written into this document; both are listed empty in `.env.example` and are ignored by `.gitignore` when filled in `.env`.

| Secret | Used for | How to generate |
|---|---|---|
| `JWT_SECRET` | HS256 signing of access tokens | `openssl rand -base64 48` |
| `CAMPUSCOIN_ENCRYPTION_KEY` | Application-level field encryption (AES-256-GCM) of `transactions.description`, `recurring_rules.description` and `bookmarks.note` | `openssl rand -base64 32` — must decode to exactly 32 bytes |

> **`CAMPUSCOIN_ENCRYPTION_KEY` is a symmetric secret, not a private key.** It is never written to MySQL, never placed in a JWT and never sent to Angular. **Back it up:** data encrypted with one key cannot be read by a build configured with a different one, and losing it makes every encrypted description and note permanently unreadable. Do not derive it from `JWT_SECRET`. See `SECURITY.md` §12.
